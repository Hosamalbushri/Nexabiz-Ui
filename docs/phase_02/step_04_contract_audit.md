## Decisions requiring explicit approval before code

1. **Define complete `UiRadioGroupField<T>` and `UiSliderField` constructors**: required values/callbacks/labels, optional description/helper/error and `requiredIndicator`, enabled/read-only rules, radio option presentation/layout, and whether slider shows a localized value. A minimal proposal is to mirror the approved checkbox/switch field metadata, use `List<UiRadioOption<T>> options` for radio and `double value/min/max`, `int? divisions` for slider, with `enabled=true` and `readOnly=false`. This is a proposal, **not an approved contract**.
2. **Approve accessible naming for standalone controls.** A minimal additive proposal is caller-supplied `String? semanticLabel` on `UiCheckbox`, `UiSwitch`, `UiRadioGroup<T>` (group name) and `UiSlider`; field variants would derive their name from `UiFieldShell.label`. Decide whether names are optional for composition within a separately named `Semantics` ancestor or required at construction. No English fallback should be generated.
3. **Approve localized slider value semantics**, if required by the accessibility gate: should callers supply a value formatter or a `String? semanticValue`, or is an application-provided ancestor semantics contract sufficient? The current approved signature has no such parameter; silently formatting `double` values in the package would conflict with localization ownership.

The upstream checkbox tri-state order and slider range preconditions can be documented/tested as implementation behavior once contracts are approved; they do not by themselves justify a new public API. The Step 04 keyboard acceptance criterion for radio arrows needs actual widget reproduction and may require an internal adapter; no public keyboard API is assumed.
